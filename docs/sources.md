# Canonical sources

Every configuration assertion in this repository must trace back to one of these
references, or carry the `SYNTHESIZED` tag. Do not introduce a Kong or Prisma
AIRS configuration field that is not backed by a page listed here.

## Kong — the guardrail extension point

| Reference | Used for |
|---|---|
| [AI Custom Guardrail plugin](https://developer.konghq.com/plugins/ai-custom-guardrail/) | Plugin existence, 3.14+ requirement, AI licence, dependency on `ai-proxy` / `ai-proxy-advanced`. Also the definition of the built-in expression variables `$(source)`, `$(conf)`, `$(content)` and `$(resp)`, and the statement that they may be used as arguments to functions but not inside a function body. `$(source)` takes the values `INPUT` while inspecting the request and `OUTPUT` while inspecting the response — `airs_contents` switches on it. `$(resp)` is documented as a Lua table in the `INPUT` phase and a string in the `OUTPUT` phase; lab testing against a Kong AI Gateway 2.0.3 data plane found it a table in both phases, including `OUTPUT` (see `docs/lab-streaming.md`). `airs_verdict` still handles the string branch for cover against a future Kong release |
| [AI Custom Guardrail reference](https://developer.konghq.com/plugins/ai-custom-guardrail/reference/) | Full config schema. **Source of truth for field names and allowed values, though it lags a running data plane.** `guarding_mode` is an enum of `BOTH` / `INPUT` / `OUTPUT`; `text_source` of `last_message` / `concatenate_user_content` / `concatenate_all_content`; `request.body`, `request.headers`, `request.queries` and `params` are flat maps of strings and are referenceable; `request.auth` (location `body` \| `header` \| `query`, `name`, `value`, `value` referenceable and encrypted) is a dedicated slot for the credential, documented but unused here; `timeout`, `ssl_verify`, `stop_on_error`, `response_buffer_size`, `allow_masking`, `metrics` and `custom_metrics` exist; `allow_masking`'s description notes that streaming is disabled when it is enabled; there are no retry or cache fields. The schema is published inline on that page as `window.schema`, which lists 13 config keys. A Kong AI Gateway 2.0.3 data plane's own `GET /schemas/plugins/ai-custom-guardrail` lists four more, not yet on this page: `rejection_mode`, `continue_on_detection`, `log_blocked_content` and `proxy_config`, since verified for both proxy pairs, http and https (real Prisma AIRS endpoint through an HTTP CONNECT proxy); credentials and `no_proxy` not exercised. See the AI Gateway changelog row below. Prefer the schema over narrative docs, and prefer a live data plane over both |
| [Example: AI Custom Guardrail with Azure Content Safety](https://developer.konghq.com/plugins/ai-custom-guardrail/examples/azure-content-safety/) | The pattern this repository follows for nested JSON: a function returning a Lua table, referenced from a flat `request.body` value. Also shows complex `params` values passed as JSON strings, the `function(resp, conf)` signature, and dotted access to a function's result field, `$(fn.field)` (`$(check_response.block)`, `$(check_response.block_message)`) — the pattern `airs_verdict.block` / `.block_message` / `.detail` follows here |
| [Example: AI Custom Guardrail with Mistral Moderation](https://developer.konghq.com/plugins/ai-custom-guardrail/examples/mistral-moderation/) | Working example of `guarding_mode: BOTH`, `text_source: concatenate_all_content`, `params`, `request.*`, `response.block`, `response.block_message`, `functions`, and the `$(conf.params.*)` / `$(content)` interpolation |
| [How-to: AI Custom Guardrail with Mistral](https://developer.konghq.com/how-to/use-ai-custom-guardrail-with-mistral/) | The same example in tutorial form, with the block response body shape |

A chunk returning `nil` removes that field from the log record, the mechanism used here to keep client credentials out of the serializer's `request.headers` / `response.headers`; the plugin pages note that `custom_fields_by_lua` applies to the shared serializer table, so the removal also affects logging plugins running after it. `path: /dev/stdout` is not mentioned by the page: LAB-VERIFIED 2026-09-14, one JSON record per request in `docker logs` on the AI Gateway data plane image |

| [HTTP Log plugin](https://developer.konghq.com/plugins/http-log/) | `custom_fields_by_lua` chunks may call the Kong PDK, not only return a literal or read another serializer field — the page's own example chunk is `return kong.request.get_header('h1')`. `airs-diagnostics-log`'s 2026-09-15 widened query-string scrub (rebuilding `request.uri` / `request.url` from `kong.request.get_path()` etc. instead of echoing the raw value) follows this pattern |

## Palo Alto Networks

| Reference | Used for |
|---|---|
| [Scan sync request endpoint](https://pan.dev/prisma-airs/api/airuntimesecurity/scan/scan-sync-request/) | The request body field by field. `contents` is "a list of prompt or response or prompt/response pairs. The last element is the one that needs to be scanned, and the previous elements are the context for the scan". Measured against a live tenant, that is literal and it is the constraint that shapes `airs_contents`: an injection sent alone blocks, the same injection as the first of two or of three elements comes back `allow` / `benign`, and as the last element it blocks again. Earlier elements are context and are **not** judged, so a scan carries one element holding everything that must be scanned. Its elements also accept `code_prompt`, `code_response`, `context` (for contextual grounding) and `tool_event`, none of which this repository populates. Also the three correlation identifiers and what each is for: `tr_id` "for correlating the prompt and response transactions", `session_id` "for tracking Sessions", both echoed back in the scan response alongside the scan ID. Both are echoed back in the scan response alongside the scan ID, which is how the round-versus-conversation mapping above was measured. The page renders its schema client-side, so fetch it in a browser rather than with a plain HTTP client |
| [Prisma AIRS AI Runtime API, developer docs](https://pan.dev/prisma-airs/api/airuntimesecurity/airuntimesecurityapi/) | Scan API endpoint, request and response schema. Also documents the 2 MB maximum payload size per synchronous scan request, relevant to `text_source: concatenate_all_content` on long conversations  Measured 2026-09-14: a payload just above 2 MB was accepted, a 3.5 MB one answered HTTP 413 \"The request body is too large\", which the guardrail turns into a fail-closed HTTP 500. |
| [aisecurity-python-sdk](https://github.com/PaloAltoNetworks/aisecurity-python-sdk) | **Source of truth for the AIRS payload.** `Metadata` accepts `app_name`, `app_user` ("end user using the AI application"), `ai_model`, `user_ip` and an `agent_meta` object (`agent_id`, `agent_version`, `agent_arn`), all optional strings; this repository populates the first four and not `agent_meta`. The generated OpenAPI client under `aisecurity/generated_openapi_client/docs/` documents `ScanRequest` (`tr_id`, `session_id`, `transaction_id`, `ai_profile`, `metadata`, `contents`), `ScanResponse` (`source`, `scan_id`, `report_id`, `tr_id`, `session_id`, `transaction_id`, `profile_id`, `profile_name`, `category`, `action`, `prompt_detected`, `response_detected`, `tool_detected`, `error`, `timeout`, `errors`), `PromptDetected`, `ResponseDetected`, `Metadata` and `AiProfile` field by field. The three correlation identifiers are all optional, and what they mean was settled by measurement rather than by reading, because the pages disagree. Against a live tenant, nine probes against `/v1/scan/sync/request`: `transaction_id` is its own slot, the **round** — a prompt and the response it produced. `tr_id` and `session_id` are **the same slot**, the conversation: a request carrying only `tr_id` comes back with `session_id` set to that value, a request carrying only `session_id` comes back with `tr_id` set to it, and when both are supplied `session_id` wins and the `tr_id` value is discarded. The endpoint page's own example body sends `tr_id` and `session_id` and no `transaction_id`; sent literally that yields a session whose every scan carries a generated `pan_<uuid>` transaction, so the prompt scan and the response scan of one turn land in different transactions — which is why this repository sends `session_id` and `transaction_id` instead. Any identifier not supplied is generated by Prisma AIRS as `pan_<uuid>`. So `tr_id` is the older name of `session_id`, not of `transaction_id`; this repository sends `transaction_id` and `session_id` and never `tr_id`. The generated model applies no length or pattern constraint to any of the three. `ScanResponse` has since grown `prompt_masked_data`, `response_masked_data`, `prompt_detection_details`, `response_detection_details`, `created_at` and `completed_at`, and `Metadata` an `agent_meta` object, none of which this repository reads yet |
| [API Intercept overview](https://docs.paloaltonetworks.com/ai-runtime-security/activation-and-onboarding/ai-runtime-security-api-intercept-overview) | Onboarding, API application creation, security profiles |
| [Detect MCP Threats, API Intercept](https://docs.paloaltonetworks.com/ai-runtime-security/administration/api-intercept-create-configure-security-profile/detect-mcp-threats) | Evidence that the MCP gap is Kong-side, not AIRS-side. Measured against a live tenant 2026-09-14, and the constraints are tighter than the page states: `tool_event.metadata.ecosystem` accepts `mcp` and refuses `openai` with HTTP 400 `unsupported ecosystem`, and `method` accepts `tools/call` and `tools/list` and refuses anything else with `unsupported method` — the same two-method allowlist [PANW's own `custom-plugin-v3` records](https://github.com/PaloAltoNetworks/prisma-airs-integrations/tree/main/Kong/custom-plugin-v3). A `tool_event` element is detected properly (`injection` firing on `input_detected`, `threats: ["context poisoning"]`), but only when it is the LAST element of `contents[]`, which would displace the prompt from the same scan. That is why this repository scans tool text inside the prompt element rather than as a `tool_event`: one scan judges one element, and a guardrail function gets one scan per phase. API Intercept accepts a `contents[].tool_event` object (`metadata.ecosystem`, `method`, `server_name`, `tool_invoked`, `input`, `output`) on `/v1/scan/sync/request` and reports findings under `tool_detected`, covering tool definition poisoning and credential leakage |
| [Use the AI Sessions and API Application Views](https://docs.paloaltonetworks.com/ai-runtime-security/administration/api-intercept-create-configure-security-profile/use-the-ai-sessions-and-application-views) | What the correlation identifiers buy. AI sessions are "logical groupings of related API calls sharing the same transaction ID", and "if no transaction ID is provided, the system automatically creates one for each atomic API call". It also states that the feature "requires your applications to send a consistent transaction ID with related API calls to properly correlate them into sessions". That wording does not match what the API does: the identifier a caller must keep consistent across the calls of one conversation is `session_id`, and `transaction_id` varies per round — see the measurement in the SDK row above. `airs_correlation` takes the session from a request header and falls back to the round, so an exchange is never split across two sessions. Supplying any of them turned out to be a configuration change after all — a guardrail function body reaches the Kong PDK, and `kong.ctx.shared` persists between the two phases (LAB-VERIFIED 2026-09-14) |
| [Prisma AIRS MCP Server](https://docs.paloaltonetworks.com/ai-runtime-security/activation-and-onboarding/prisma-airs-mcp-server-for-centralized-ai-agent-security/understanding-the-prisma-airs-mcp-server) | The path available today for MCP coverage, outside the gateway: the agent invokes the scan itself |
| [prisma-airs-integrations](https://github.com/PaloAltoNetworks/prisma-airs-integrations) | Official Kong assets: custom Lua plugin v1 and v2, `request-callout` variant. `Kong/custom-plugin-v2/handler.lua` and `Kong/request-callout/request-callout-prisma-airs-config.json` confirm the wire payload, the `x-pan-token` header, and the fail-closed verdict mapping. The `request-callout` config is also the source for this repository's generic client-facing block body: it returns HTTP 403 with a generic "Blocked by AI security scan" rather than naming the detection to the caller |
| [prisma-airs-integrations, custom-plugin-v3](https://github.com/PaloAltoNetworks/prisma-airs-integrations/tree/main/Kong/custom-plugin-v3) | Added alongside the v1/v2 assets above (merged 2026-09-11); the upstream README lists all four integrations. Three flavours: `prisma-airs-intercept` (raw provider body, MCP-aware, buffered SSE scanning, DLP masking, regional endpoints, monitor mode), `prisma-airs-intercept-postproxy` (after AI Proxy normalisation), and a config-only `request-callout` flavour for Konnect Serverless. Its own deployment guide recommends `ai-custom-guardrail` wherever it covers the routes, keeps the Lua plugin for MCP and for streamed-response scanning, and cites this repository as the worked reference for AI Gateway 2.x |
| [Prisma AIRS Intercept plugin on Kong hub](https://developer.konghq.com/plugins/prisma-airs-intercept/) | Third-party plugin, Kong Gateway 3.4+, custom image required |

## Verification note

Narrative documentation pages describe behaviour. The **plugin schema** describes
what will actually apply. When the two disagree, the schema wins — the plugin
overview page, for instance, does not mention `guarding_mode` at all, while the
schema pins its three allowed values. Retrieve the schema from a running data
plane rather than trusting a documentation page or a previous session's memory.
